# Database Migrations Guide

This guide covers how to manage database schema changes using Alembic and SQLModel.

## Quick Reference

### Essential Commands

```bash
# Navigate to database package
cd packages/database

# Generate new migration from model changes
alembic revision --autogenerate -m "Description of changes"

# Apply all pending migrations
alembic upgrade head

# Apply specific migration
alembic upgrade +1          # Apply next migration
alembic upgrade <version>   # Apply specific version

# Rollback migrations
alembic downgrade -1        # Rollback one migration
alembic downgrade base      # Rollback to empty database

# Check migration status
alembic current             # Show current version
alembic history             # Show migration history
alembic heads               # Show latest migrations

# Show SQL without executing
alembic upgrade head --sql

# Create empty migration (manual changes)
alembic revision -m "Manual migration"
```

## Workflow

### 1. Development Workflow

```bash
# 1. Make changes to SQLModel models in src/models.py
# 2. Generate migration
cd packages/database
alembic revision --autogenerate -m "Add user preferences"

# 3. Review generated migration file
#    Location: alembic/versions/<hash>_add_user_preferences.py

# 4. Apply migration
alembic upgrade head

# 5. Test your application
```

### 2. Production Deployment

```bash
# 1. Generate SQL for review
alembic upgrade head --sql > migration_$(date +%Y%m%d_%H%M%S).sql

# 2. Apply migrations
alembic upgrade head

# 3. Verify
alembic current
```

## Key Concepts

### 1. SQLModel Models (Source of Truth)
- Defined in `src/models.py`
- Used by your application
- Alembic compares these to database to generate migrations

### 2. Migration Files
- Generated by Alembic in `alembic/versions/`
- Contain `upgrade()` and `downgrade()` functions
- Never edit applied migrations (create new ones instead)

### 3. Version Tracking
- `alembic_version` table in database tracks applied migrations
- Each migration has unique revision ID (e.g., `423efb1a2df4`)

## Common Scenarios

### Adding a New Table

1. Add new SQLModel class to `models.py`:
```python
class NewTable(SQLModel, table=True):
    id: UUID = Field(default_factory=uuid4, primary_key=True)
    name: str = Field(max_length=255)
    created_at: datetime = Field(default_factory=datetime.utcnow)
```

2. Generate and apply migration:
```bash
alembic revision --autogenerate -m "Add new_table"
alembic upgrade head
```

### Adding a Column

1. Add field to existing model in `models.py`:
```python
class User(UserBase, table=True):
    # ... existing fields ...
    phone_number: Optional[str] = Field(default=None, max_length=20)
```

2. Generate and apply migration:
```bash
alembic revision --autogenerate -m "Add phone_number to users"
alembic upgrade head
```

### Modifying a Column

1. Update field definition in `models.py`:
```python
# Change from:
# email: str = Field(max_length=100)
# To:
email: str = Field(max_length=255, unique=True)
```

2. Generate and apply migration:
```bash
alembic revision --autogenerate -m "Increase email length and add unique constraint"
alembic upgrade head
```

### Data Migrations

For data changes (not schema), create manual migration:

```bash
# Create empty migration
alembic revision -m "Backfill user display names"

# Edit the migration file to add data operations
```

Example data migration:
```python
def upgrade() -> None:
    # Update existing records
    op.execute("""
        UPDATE users 
        SET display_name = COALESCE(full_name, email)
        WHERE display_name IS NULL
    """)

def downgrade() -> None:
    # Cannot easily undo data changes
    pass
```

## Best Practices

### 1. Migration Guidelines
- **One logical change per migration** - Keep migrations small and focused
- **Descriptive names** - Use clear names like `add_index_to_users_email`
- **Review autogenerated migrations** - Alembic isn't perfect, check the SQL
- **Test downgrades** - Ensure you can rollback if needed
- **Never edit applied migrations** - Create a new migration instead

### 2. Development Tips
- **Run migrations locally first** - Test before deploying to production
- **Use transactions** - Alembic runs migrations in transactions by default
- **Backup before major changes** - Especially for production databases
- **Document breaking changes** - Note any API or data model changes

### 3. Team Collaboration
- **Commit migration files** - Include in version control
- **Apply migrations in order** - Don't skip versions
- **Communicate schema changes** - Let team know about breaking changes
- **Use migration branches carefully** - Avoid merge conflicts in migration files

## Troubleshooting

### Common Issues

#### "Target database is not up to date"
```bash
# Check current state
alembic current

# If migrations are out of sync, you may need to:
# 1. Apply missing migrations: alembic upgrade head
# 2. Or mark as applied: alembic stamp head
```

#### "No changes detected" but models changed
- Ensure `target_metadata` is set correctly in `alembic/env.py`
- Check that models are imported in `env.py`
- Verify database connection is working

#### Circular dependencies in migrations
If you get foreign key errors during migration:
1. Create tables without foreign keys first
2. Add foreign keys in a separate migration
3. Or manually edit the migration file to reorder operations

#### Migration conflicts
If two developers create migrations simultaneously:
```bash
# 1. Check which migrations are applied
alembic current

# 2. Rename conflicting migration files to maintain order
# 3. Update down_revision in migration files if needed
```

## Integration with Docker

### Current Setup
The PostgreSQL container no longer uses `init.sql`. Instead:

1. Database starts empty
2. Application runs migrations on startup
3. Schema is created by Alembic

### Adding Migration Step to Startup
Add to your API/worker Dockerfile or startup script:
```bash
# Run migrations before starting app
cd /packages/database
alembic upgrade head

# Start application
python -m app.main
```

### Environment Variables
Ensure these are set for migrations:
```bash
DATABASE_URL=postgresql://user:password@host:port/database
```

## Advanced Topics

### Multiple Databases
For multiple database support, modify `alembic/env.py` to:
- Handle multiple engines
- Use `context.config.get_section()` for different configs
- Route migrations based on table names

### Custom Migration Templates
Edit `alembic/script.py.mako` to customize:
- Migration file structure
- Import statements
- Documentation format

### Testing Migrations
```bash
# Test on clean database
createdb test_db
DATABASE_URL=postgresql://localhost/test_db alembic upgrade head

# Test downgrade
DATABASE_URL=postgresql://localhost/test_db alembic downgrade base
```

If you encounter issues:
1. Check `alembic.ini` configuration
2. Verify database connection
3. Review migration file for syntax errors
4. Check Alembic logs for detailed error messages

Remember: **Never run `DROP TABLE` or `DELETE` in `upgrade()` without proper `downgrade()` logic!**
