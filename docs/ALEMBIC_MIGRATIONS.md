# Alembic Migrations Guide

This guide explains how to use Alembic for database migrations in the 30ai project.

## What is Alembic?

Alembic is a database migration tool for SQLAlchemy. It allows you to:
- Version control your database schema
- Generate migrations automatically from model changes
- Apply and rollback migrations safely
- Maintain database consistency across environments

## Project Structure

```
apps/api/
├── alembic/              # Alembic configuration
│   ├── versions/         # Migration files
│   ├── env.py           # Migration environment
│   └── script.py.mako   # Migration template
├── alembic.ini          # Alembic configuration file
└── src/                 # Application code
```

## Setup

### 1. Install Dependencies

Make sure you have the required dependencies installed:

```bash
cd apps/api
uv sync
```

### 2. Configure Database URL

Update the database URL in `alembic.ini` or set the `DATABASE_URL` environment variable:

```ini
sqlalchemy.url = postgresql://30ai_user:30ai_password@localhost:5432/30ai_db
```

Or use environment variable:
```bash
export DATABASE_URL=postgresql://30ai_user:30ai_password@localhost:5432/30ai_db
```

## Using Alembic

### Makefile Commands

The easiest way to use Alembic is through the Makefile:

```bash
# Start database services
make db-up

# Initialize database with migrations
make db-init

# Create a new migration
make db-migrate message="Add user profile field"

# Apply all pending migrations
make db-upgrade

# Revert last migration
make db-downgrade

# Show migration history
make db-history

# Show current migration
make db-current

# Stop database services
make db-down
```

### Manual Commands

You can also run Alembic commands directly:

```bash
cd apps/api

# Initialize Alembic (first time only)
alembic init alembic

# Create a new migration
alembic revision --autogenerate -m "Description of changes"

# Apply migrations
alembic upgrade head

# Revert one migration
alembic downgrade -1

# Revert to specific migration
alembic downgrade <revision_id>

# Show current migration
alembic current

# Show migration history
alembic history

# Show migration history with details
alembic history --verbose
```

## Migration Workflow

### 1. Development Workflow

1. **Make model changes**: Update your SQLModel models in `packages/database/src/models.py`
2. **Generate migration**: `make db-migrate message="Your change description"`
3. **Review migration**: Check the generated migration file in `alembic/versions/`
4. **Apply migration**: `make db-upgrade`
5. **Test**: Verify your changes work correctly

### 2. Production Deployment

1. **Pull latest code**: `git pull`
2. **Apply migrations**: `make db-upgrade`
3. **Verify**: Check that migrations applied successfully

## Creating Migrations

### Automatic Migration Generation

Alembic can automatically detect changes to your SQLModel models:

```bash
# After changing your models
make db-migrate message="Add new field to documents"
```

This will:
1. Compare current database schema with your models
2. Generate a migration script with the necessary changes
3. Create a new file in `alembic/versions/`

### Manual Migration Creation

For complex changes, create a migration manually:

```bash
alembic revision -m "Complex schema change"
```

Then edit the generated migration file to implement the changes.

## Migration Files

Migration files have a specific structure:

```python
"""Add user profile field

Revision ID: abc123def456
Revises: previous_revision_id
Create Date: 2024-01-01 12:00:00.000000

"""
from alembic import op
import sqlalchemy as sa
from sqlalchemy.dialects import postgresql

# revision identifiers, used by Alembic.
revision = 'abc123def456'
down_revision = 'previous_revision_id'
branch_labels = None
depends_on = None


def upgrade() -> None:
    # Add column
    op.add_column('users', sa.Column('profile_picture', sa.String(), nullable=True))
    
    # Create index
    op.create_index('idx_users_email', 'users', ['email'], unique=True)
    
    # Modify column
    op.alter_column('documents', 'file_size',
               existing_type=sa.INTEGER(),
               type_=sa.BigInteger(),
               existing_nullable=True)


def downgrade() -> None:
    # Reverse the changes
    op.drop_index('idx_users_email', table_name='users')
    op.drop_column('users', 'profile_picture')
    op.alter_column('documents', 'file_size',
               existing_type=sa.BigInteger(),
               type_=sa.INTEGER(),
               existing_nullable=True)
```

## Best Practices

### 1. Always Review Generated Migrations

Autogenerated migrations are not always perfect. Always review the generated SQL before applying.

### 2. Write Reversible Migrations

Ensure your `downgrade()` method correctly reverses the `upgrade()` changes.

### 3. Use Descriptive Messages

Use clear, descriptive messages for migrations:
- ❌ Bad: `update models`
- ✅ Good: `add email verification field to users table`

### 4. Test Migrations

Test migrations in a development environment before applying to production.

### 5. Backup Before Major Changes

Always backup your database before applying major migrations.

### 6. Use Transactions

Alembic runs migrations in transactions by default. For PostgreSQL, some operations (like CREATE INDEX CONCURRENTLY) cannot run in transactions.

## Common Operations

### Adding a Table
```python
def upgrade():
    op.create_table(
        'new_table',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('name', sa.String(), nullable=True),
        sa.PrimaryKeyConstraint('id')
    )

def downgrade():
    op.drop_table('new_table')
```

### Adding a Column
```python
def upgrade():
    op.add_column('table_name', sa.Column('new_column', sa.String(), nullable=True))

def downgrade():
    op.drop_column('table_name', 'new_column')
```

### Creating an Index
```python
def upgrade():
    op.create_index('idx_table_column', 'table_name', ['column_name'])

def downgrade():
    op.drop_index('idx_table_column', table_name='table_name')
```

### Modifying a Column
```python
def upgrade():
    op.alter_column('table_name', 'column_name',
                    existing_type=sa.String(50),
                    type_=sa.String(100),
                    nullable=False)

def downgrade():
    op.alter_column('table_name', 'column_name',
                    existing_type=sa.String(100),
                    type_=sa.String(50),
                    nullable=True)
```

## Troubleshooting

### "Can't locate revision identified by X"
This usually means the migration history is corrupted. You can:
1. Check `alembic_version` table in your database
2. Manually update the version if needed
3. Use `alembic stamp` to mark a specific revision

### "No changes detected"
Make sure:
1. Your models are imported in `env.py`
2. You're comparing against the correct database
3. Your model changes are actually different from the database schema

### "Relation already exists"
You're trying to create a table/column that already exists. Check your migration history.

### Connection Issues
Verify:
1. Database is running
2. Connection URL is correct
3. You have proper permissions

## Advanced Topics

### Multiple Databases
For multiple databases, you can use Alembic's `--name` parameter or create separate Alembic configurations.

### Data Migrations
For migrating data (not just schema), you can use `op.execute()`:

```python
def upgrade():
    # Schema change
    op.add_column('users', sa.Column('status', sa.String(), default='active'))
    
    # Data migration
    op.execute("UPDATE users SET status = 'active' WHERE status IS NULL")
```

### Custom Migration Templates
You can customize the migration template in `script.py.mako`.
